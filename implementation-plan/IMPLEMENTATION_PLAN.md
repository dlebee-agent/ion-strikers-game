## 1. What the existing implementation actually is

A complete, shipping, browser-based team FPS. Roughly 9,500 lines across
client, server and shared modules, currently live on `game.ionstrikers.com`.

| Area | File | Lines |
|---|---|---|
| Authoritative server, rooms, bots, rules | `server.js` | 1,646 |
| Client: render, movement, netcode, HUD, menus | `public/game.js` | 5,750 |
| Screen manager | `public/ui.js` | 80 |
| Hitbox/hitscan maths, shared verbatim | `public/hitbox.js` | 96 |
| Ragdoll (verlet over the skeleton) | `public/ragdoll.js` | 349 |
| Markup: HUD + all menu screens | `public/index.html` | 685 |
| Menu visual language | `public/menu.css` | 284 |
| Map loader + 7 map definitions | `maps-loader.js`, `public/maps/*.data.js` | ~600 |

**Shape today.** One Node process is both the HTTP file server and the WebSocket
game server (`server.js:30`, `server.js:68`). It holds a `Map` of `Room`
objects; each `Room` owns players, bots, score, round state and a map reference.
Clients connect over a single WebSocket carrying JSON, and every message is a
flat `{t: '...'}` object.

**Client→server:** `join`, `state`, `shot`, `melee`, `specialStart`,
`specialFire`, `setTeam`, `teamMenu`, `chat`, `ping`, `listRooms`, `leave`.

**Server→client:** `init`, `snap`, `hit`, `tracer`, `melee`, `special`,
`announce`, `meteor`, `roundStart`, `roundEnd`, `matchOver`, `team`,
`teamOpts`, `teamDenied`, `respawn`, `rooms`, `joinError`, `chat`, `pong`.

That message set is a good starting inventory for the new protocol (§15); the
semantics are sound even though the encoding is not.

**What is genuinely good and must survive:** the movement feel (§4), the
hitbox/lag-compensation model, the HUD and menus (§3), the map data format, the
announcer, and the server-authority discipline — the client already sends
*intent* (`shot` carries a ray; the server decides the hit) and never asserts
damage, kills or score.

**What must not be carried over:** the encoding (§15), the
single-process-does-everything shape, and the state-reset-by-enumeration pattern
(§5).

**The one real animation risk.** The pack has no pistol-carrying locomotion, so
the client *bakes* gun-ready tracks at load: it takes each movement clip, keeps
every lower-body curve, freezes the `clavicle_r` chain at the pistol-idle pose,
and counter-rotates `spine_01` to cancel the movement clip's pelvis pitch
(`public/game.js:471`–`578`, `buildGunReadyTracks`). The same trick produces the
FP punch (`buildFPPunchTrack`, `public/game.js:790`).

In Godot this is **not** a runtime bake. Recommendation: do it **offline** as an
import-time step producing real `Animation` resources, then drive them from an
`AnimationTree` with an upper/lower body blend on the `spine_01` bone. Rationale:
Godot's `AnimationTree` has a first-class blend/filter mechanism for exactly this
(per-bone filters on a `Blend2`/`BlendTree`), which is a cleaner expression of the
intent than curve surgery, and moving it offline removes ~100 lines of load-time
work from the client. **Alternative rejected:** porting `buildGunReadyTracks`
literally to C++ — it would reproduce a workaround for a PlayCanvas limitation
that Godot does not have.

### 2.3 Maps — lift the box limit, keep a collision proxy

**This section was revised after review.** The first draft recommended keeping
the box-only data format and rejecting Godot scenes. That reasoning was inherited
from a constraint that does not exist in Godot, and it was wrong.

**Why the current format is boxes.** Seven maps are plain data modules
(`public/maps/*.data.js`): id, name, arena radius, a procedural sky spec, and a
`shapes` array of boxes with optional rotation, height offset and a `top`
(standable) flag. `maps-loader.js` is shared by client and server so both build
identical colliders. That sharing exists because **neither side has a physics
engine** — a browser JS client and a Node server, so they hand-rolled a collider
both could run, and a hand-rolled collider is only cheap if everything is a box.
It is a workaround for the old stack, not a design goal.

**None of that constrains Godot.** Confirmed in the 4.7.2 module list: `jolt_physics`
and `godot_physics_3d` (Jolt is the default 3D engine since 4.4), `csg` for
authoring, `gridmap`, `navigation_3d`, and — directly relevant — `vhacd`,
in-engine convex decomposition. Trimesh (`ConcavePolygonShape3D`), convex hulls,
heightmaps and primitives are all available for static level geometry. And in the
new architecture **both client and server are Godot**, so "share the source of
truth" no longer implies "share a box list" — they can load the same scene.

**Recommendation: author maps as Godot scenes, and bake a collision proxy.**

- **Visuals:** arbitrary geometry. Ramps, curves, detailed meshes, real materials
  — everything the box format forbids. Authored in the Godot editor, which is a
  far better tool than the bespoke web editor the project maintains today.
- **Collision:** a proxy generated at import — convex hulls (V-HACD is in-engine)
  or collision volumes the author places explicitly. The proxy, not the visual
  mesh, is what the character controller runs against.

**Why a proxy rather than just using the render mesh.** It keeps the movement
controller (§4, §8) engine-free, deterministic and unit-testable without a
display server, and keeps client prediction and server simulation running
*identical* code — the property that makes the current game's predicted impacts
agree with its authoritative ones. Convex-only collision is also what a
Source-style controller wants; trimesh against a swept capsule is where
character controllers acquire their worst edge cases. Visual mesh ≠ collision
hull is standard practice in shooters for exactly this reason.

**The seven existing maps port mechanically.** A one-off tool reads each
`*.data.js` and emits a Godot scene of boxes plus the matching proxy — nothing is
lost, and each map can then be enriched in the editor at leisure. Note the maps
are authored half-and-mirrored (`public/maps/parkour.data.js`: "authored for the
BLUE half and mirrored to the red half"); that symmetry convention is worth
keeping in whatever authoring flow replaces it.

**Consequence for the map editor.** `editor-server.js` / `public/editor.js` /
`.pi/skills/map-authoring/SKILL.md` become redundant once authoring moves into
the Godot editor. That is a *gain* — one less bespoke tool — but it is a real
piece of working software being retired, so it belongs on the decision list
(§23.2) rather than being dropped silently.

### 2.4 UI assets — there are none

`find public -name '*.png' -o -name '*.svg' …` returns **nothing**. The entire
HUD and menu system is CSS, text, and a handful of Unicode glyphs (`◆`, `✷`,
`☠`, `👤`, `👊`, `⌨`, `⛶`). Two consequences:

1. There is no icon atlas to port — §3 is a Theme-and-Control job.
2. The two fonts are pulled from the Google Fonts CDN at

## 3. Preserving the HUD and menus

This is the part the brief is most emphatic about, and the existing structure
makes it tractable — because the current UI is already organised around a rule
that maps cleanly onto Godot.

### 3.1 The rule already exists

`UI.md` states it: **redrawn every frame or anchored to a world
position → engine UI; event-driven or needs text input → DOM.** In Godot both
halves are `Control` nodes, so the rule relaxes, but the *classification* it
produced is still the right decomposition and should be carried over verbatim.

### 3.2 Screens and layers → CanvasLayer tree

`public/ui.js` implements a screen manager worth reproducing exactly:

- A **screen** is full-viewport and **exclusive** — `Ui.show(name)` reveals one
  and hides every other *and everything parented to it*.
- A **layer** is a container inside a screen for runtime-built widgets. Nothing
  is ever appended to `document.body`.
- Some layers **float** across named screens (`data-on`), which is how chat spans
  match + match-over without being duplicated.

The comment at `public/ui.js:12` records *why*: the "sticky scoreboard" bug
existed because match widgets were parented to `<body>` and outlived the match
that owned them. That is the same class of defect the new architecture is
trying to prevent in gameplay state (§5) — the UI already learned this lesson and
the fix should not be thrown away.

**Proposed mapping.** A `UiRoot` node owning one `CanvasLayer` per screen, with
`Ui.show(name)` → set exactly one visible. Screens: `callsign`, `menu`, `join`,
`create`, `settings`, `match`, `matchover`, `viewer`. Floating layers:
`menuchrome`, `comms`, `match`, `matchover`, `dialogs`. Same names, same
exclusivity, same "no orphan widgets" guarantee. The structural tests in
`test/ui.test.mjs` (151 assertions) encode this contract and their
intent should be re-expressed as Godot tests.

### 3.3 Visual language → a Theme resource

`public/menu.css:9` defines the design tokens explicitly:

```
--cy #4ee2f5   --rd #f43f5e   --rd-soft #ff6b83
--ink #e9edf6  --ink-2 #c6cee2  --mute #9aa6c2  --mute-2 #6d7d9c  --mute-3 #55637f
--line rgba(233,237,246,.1)     --panel rgba(12,11,22,.8)  --panel-2 #0b0a16
Chakra Petch (headings) · IBM Plex Mono (labels, stats)
```

Team colours are `#2b6cff` blue / `#ff4b57` red (`public/index.html:77`).

These become a single Godot `Theme` with named colours/fonts/styleboxes. Panels
use a radial-gradient background (`menu.css:29`) — reproducible with a
`StyleBoxTexture` or a small shader.

### 3.4 HUD inventory (all of it must reappear)

From `public/index.html:251`–`290`: crosshair, `score` (blue / mid label /
red), `hp`, `ammoWrap`/`gunName`, `devHud`, `specialHud` (+ text + charge bar),
`kfeed` (kill feed), `center` (big centre message), `teamPanel` (+ counts +
pick buttons), `keysPanel`, and the four HUD buttons (keys / team / fullscreen /
leave). Plus runtime widgets: announce banner, leaderboard, victory board,
match-over card, spectator panel, touch controls.

### 3.5 Mobile controls — in scope only if "native" includes mobile (§23.9)

Non-trivial and recently tuned: landscape gate, one movement stick, drag-to-aim
with **tap-to-shoot** (a tap is <350 ms **and** <16 px of total travel), plus
FIRE / JUMP / CROUCH / WALK / ✷SPECIAL laid out so nothing overlaps at 844×390
*or* 667×375. The overlap constraint is currently enforced by a test that
rectangle-checks every control against every other. Port the layout **and** that
test.

### 3.6 The Skins screen — improve, and gate behind dev mode

Per instruction, the one exception. Today it is `data-screen="viewer"`: a
free-move/preview/first-person model viewer with a clip dropdown
(`public/game.js:4222`+). Proposal:

- Rebuild it as a proper **content inspection tool**: model, animation list,
  attachment points, team tint, and the special-attack preview.
- **Only reachable when the server reports dev mode.** The mechanism already
  exists — `DEV_MODE` (`server.js:130`) is advertised to clients as `dev` on the
  room-list message, and the create screen already reveals a dev-only option
  from it. The Skins entry uses the same gate, so a production client cannot
  reach it at all.

|---|---|---|
| Unit scale | 1 source unit = 0.0254 m | `game.js:21` |
| Run speed | 260 u/s (6.60 m/s) | `game.js:22` |
| Walk modifier | 0.52 | `game.js:23` |
| Duck modifier | 0.34 | `game.js:62` |
| `sv_accelerate` | 5.5 | `game.js:24` |
| `sv_airaccelerate` | 12 | `game.js:25` |
| Air speed cap | 30 u/s | `game.js:26` |
| `sv_friction` | 5.2 | `game.js:27` |
| `sv_stopspeed` | 80 u/s | `game.js:28` |
| Gravity | 800 u/s² | `game.js:29` |
| Jump impulse | 301.993377 u/s | `game.js:33` |
| Step height / lip | 0.6 m / 0.35 m | `game.js:38`, `game.js:45` |
| Step view smoothing | 4.0 m/s catch-up, ≤0.40 m | `game.js:58` |
| Player radius | 0.4 m | `game.js:63` |
| Fire delay | 140 ms | `game.js:66` |
| Spawn protection | 2200 ms | `game.js:65` |

Hitboxes are shared verbatim between client and server via `public/hitbox.js`
(loaded by the server at `server.js:160`) — a vertical capsule plus a separate
head sphere, measured against the rendered rig:

```
stand:  foot 0.30  chest 1.35  r 0.26   head 1.60  headR 0.19   eye 1.60
crouch: foot 0.24  chest 0.90  r 0.28   head 1.12  headR 0.19   eye 0.90
```

**Keep this module shared.** It is the reason the client's predicted impact and
the server's authoritative damage agree, and the comment at `hitbox.js:1` says so.
In the new build it belongs in `shared/game-core/`.

Weapon and combat behaviour to preserve: hitscan, 34 body / 100 head damage
(`server.js` `handleShot`), 140 ms cadence, melee as a one-hit kill at 2.6 m
within a ~70° arc on a 650 ms cooldown (`server.js:1106`), and the five-frag
special (45 m beam, 4.5 m lethal radius along the line, meteor-equivalent blast
at the impact, 300 ms minimum wind-up, 5 s auto-fire cap, non-cancellable).

Rules: Classic = 10 rounds to win, round ends when a side is wiped, 3.5 s round
end delay. Deathmatch = 50 team kills default (5–200), 5 s respawn. Rooms:
2–16 players (12 default) plus 1–24 spectator seats. Teams are balance-checked
on every join and switch; switching costs a life.

## 5. State leakage found in the reference implementation, and how ownership prevents it

The brief asks for this specifically. Four findings, all real:

**5.1 Reset-by-enumeration.** `Room.resetMatch()` (`server.js`) is a
hand-maintained list of fields to set back:

```js
this.uuid = …; this.score = {red:0,blue:0}; this.roundNum = 1;
this.roundEndAt = 0; this.matchOver = false; this.winner = null;
this.roundState = 'active'; this._firstBloodDone = false;
this._matchPointAnnounced = false;
for (const p of this.players.values()) { p.kills = 0; … }
```

Every new piece of match state adds a line here, and forgetting one is a silent
bug. **Which has already happened —**

**5.2 A meteor survives the match it was scheduled in.** `pendingMeteor` and
`nextMeteorAt` are set in `armMeteor()` (`server.js:812`) and are **not** cleared
by `resetMatch()` or `endMatch()`. `meteorImpact()` no-ops while `roundState !==
'active'`, so a meteor armed just before a match ends sits in the field until the
next match sets `roundState = 'active'` — and then lands on it. Cosmetically
minor, structurally exactly the bug class the rebuild is meant to make
impossible.

**5.3 Round state and life state were conflated.** Until recently `spawn()`
reset the kill streak — and `spawn()` is also how a *round* starts, so every
round boundary wiped every streak. In a 3v3 Classic round, which can only contain
three kills, a five-kill streak was therefore unreachable. Fixed by moving the
reset to the death paths and `resetMatch()`, but the root cause was a lifetime
question answered implicitly.

**5.4 Score outlives the body deliberately.** `ws.record = {name, k, d}`
(`server.js`) carries kills/deaths across a trip to the stands, because a player
entity is destroyed and recreated on a team change. This one is *correct*, and it
shows the model needs an explicit **participant** lifetime distinct from the
**pawn** lifetime.

**How the new model answers all four.** `GameInstance → Match → Round` with
destruction rather than reset: a new match constructs a new `Match` object and
drops the old one, so 5.1 and 5.2 cannot occur — there is no field list to
forget, and a timer owned by a destroyed `Match` dies with it. A `Round` owns
only what is round-scoped, making 5.3 a compile-time-visible decision (which
object does the streak live on?) rather than an accident. And 5.4 becomes
`Participant` (match-lifetime: identity, score) vs `Pawn` (life-lifetime:
position, health) — the distinction the current code expresses with a side-map on
a socket.

## 6. Proposed repository tree

Validated against the plan's §13.1 target, with the deltas explained beneath.

```
ion-strikers-game/
  api/                        # Go Game API (module: ionstrikers.com/api)
    cmd/gameapi/
    internal/{discovery,lobby,serverreg,auth,httpapi,config}/
  game/                       # Godot client project (project.godot lives here)
    scenes/{boot,menu,match,viewer}/
    ui/{theme,screens,hud,mobile}/
    assets/                   # imported content (see §2)
  server/                     # Godot headless server project
    scenes/
  native/                     # GDExtension C++ (godot-cpp)
    src/{client,server,shared}/
    SConstruct
  shared/
    game-core/                # pure C++: movement, hitbox, rules, map data
    protocol/                 # versioned wire schema + generated codecs
    networking/               # QUIC transport abstraction
  content/
    maps/                     # *.data.js -> canonical map data (see §2.3)
    tools/                    # extract-fp-arms, animation bake, map editor
  tests/{unit,lifecycle,protocol,integration,soak}/
  tools/
  docs/{adr,architecture}/
  deploy/
```

Deltas from the plan's sketch, and why:

- **`native/` split out from `game/`+`server/`.** One GDExtension binary is built
  once and loaded by both Godot projects. Nesting C++ under either would imply
  two builds or a dependency between the two projects.
- **`content/` instead of `assets/` at root.** `game/assets/` is what Godot
  imports; `content/` holds *sources* and the tools that produce them. Keeping
  the distinction visible prevents source files being shipped in the export.

## 7. Godot and bootstrap — verified, not remembered

Checked against upstream on 2026-08-30:

| Component | Current | Evidence |
|---|---|---|
| Godot engine | **4.7.2-stable**, released 2026-08-18 | `api.github.com/repos/godotengine/godot/releases/latest` |
| godot-cpp newest **stable tag** | **godot-4.5-stable**, 2025-09-15 | godot-cpp tags |
| godot-cpp `master` (v10.x) | **Beta** | godot-cpp README: *"The master branch of godot-cpp (version 10.x) is currently in Beta."* |
| godot-cpp releases since | `10.0.0-rc1`, `10.0.0-rc2` | godot-cpp releases |

**There is no `godot-4.6-stable` or `godot-4.7-stable` godot-cpp tag.** The
architecture plan forbids beta/RC builds, so the newest engine and the newest
bindings cannot both be taken.

**Recommendation: Godot `4.7.2-stable` + godot-cpp `godot-4.5-stable`, built with
`api_version=4.5`.** This is safe by the compatibility rule the godot-cpp README
states plainly: *"GDExtensions targeting an earlier version of Godot should work
in later minor versions, but not vice-versa."* A 4.5-targeted extension is
supported under 4.7.x; the reverse would not be.

Alternatives considered:

- **Godot 4.5-stable + godot-cpp godot-4.5-stable.** An exactly matched pair, at
  the cost of two minor versions of engine fixes. Deferred, not rejected — see
  §23, this is the decision most worth a second opinion.
- **godot-cpp `10.0.0-rc2` / `master`.** Rejected: the plan forbids RC/beta and
  upstream itself labels it Beta.
- **Engine module / fork instead of GDExtension.** Rejected: requires building
  and distributing a custom engine and editor for every contributor, for no
  benefit this project needs. Revisit only if profiling shows the GDExtension
  boundary is a measured bottleneck.

Bootstrap uses official tooling only: `godot --headless` for project creation and
export, `scons` for godot-cpp per its documented flow. Versions pinned in
`.godot-version` and a lockfile; CI asserts the pins (§21).

## 8. C++ boundaries

Three layers, with a hard rule: **`shared/game-core/` does not include
godot-cpp.**

- **`shared/game-core/`** — pure C++17/20, no engine types. Movement integrator
  (the §4 constants), hitbox/hitscan (`public/hitbox.js` ported
  1:1), map data + collider derivation (`maps-loader.js`), rules for Classic and
  Deathmatch, the special, the streak model. Unit-testable without a display
  server, which is what makes §20 affordable.
- **`shared/protocol/`** — message definitions, versioning, encode/decode. No
  gameplay.
- **`native/src/{client,server}/`** — the only code that touches godot-cpp.
  Node classes, scene wiring, input, rendering, the server's `GameServer` /
  `GameRegistry` / `GameInstance`.

Rationale: the current implementation's biggest structural asset is that
`hitbox.js` is *literally the same file* on both sides. `game-core` generalises
that property; it is also what lets the whole rules layer be tested headlessly.

## 9. Go API boundaries

Module `ionstrikers.com/api`, `cmd/gameapi` as the only binary.

- `internal/serverreg` — Game Server registration, heartbeat, capacity, build and
  protocol version, TTL eviction.
- `internal/discovery` — the joinable-lobby list. Direct successor of today's
  `roomList()` (`server.js`), which already returns name, players, humans, max,
  spectators, capacity, round, score, mode, map, and `botsShoot`.
- `internal/lobby` — create/join orchestration against the Game Server's
  management API.
- `internal/auth` — short-lived join credentials.
- `internal/httpapi` — HTTP handlers, versioning, rate limits. **JSON over
  HTTPS** (§15.1); the API never speaks the binary game protocol.
- `internal/config` — typed config; **no globals**.

The API never sees a game packet. Server selection in V1 is "the one configured
managed server" behind an interface that a scheduler can implement later.

## 10. One binary, two policies

`GameServer` reads a `HostingPolicy`:

## 11. Ownership and lifetimes

```
Process
└── GameServer            config, logging, metrics, identity, QUIC transport
    └── GameRegistry      id → GameInstance, capacity accounting
        └── GameInstance  lobby metadata, connections, mode, map, participants
            └── Match     match score, limits, match timers
                └── Round  (Classic only) round score, spawns, round timers
                    └── Pawn   position, health, per-life state
```

Rules that make §5 impossible by construction:

1. **Ending a match destroys the `Match`.** No `resetMatch()`, no field list.
2. **Timers belong to the object whose lifetime they may not outlive.** A meteor
   scheduled by a `Match` is owned by that `Match` and dies with it (fixes 5.2 by
   construction).
3. **Deathmatch has no `Round`.** The plan is explicit that DM should not be
   forced into a round abstraction; `Match` runs continuously with join-in-progress.
4. **`Participant` (match) vs `Pawn` (life)** — §5.4. Score, identity and streak
   live on the participant; position and health on the pawn. This is the
   type-level answer to "does the streak survive a round?"
5. **No mutable gameplay state in autoloads.** Process services may be global;
   lobby/match/round state is reachable only through the tree above.

## 12. Create and join

**Create:** client → `POST /v1/games` → API checks the configured server's
capacity → server `GameRegistry.create()` → API returns `{game_id, endpoint,
join_token}` → client connects over QUIC and presents the token.

**Join:** client → `GET /v1/games` → list → `POST /v1/games/{id}/join` → API
validates availability and returns endpoint + token → QUIC.

Create options stay small, matching today's create screen
(`public/index.html:365`+): mode, map, rounds *or* kill target,
player slots, spectator slots, bots on/off, optional server name — plus the
dev-mode-only "bots shoot back" toggle.

**Preserved joining rule.** Today *every* arrival lands in the stands and picks a
side explicitly, and the team menu greys out illegal choices with the reason
(`teamOptions()`, `server.js`). It is good design — an explicit choice that always
passes the balance check — and should be kept.

## 13. Transport — ENet reliable-UDP (settled)

**Decided: the client is native. Browser support is out of scope.** That closes
the only question this section had and reduces it to one transport.

The brief names QUIC. This section recommends **ENet instead**, raised under the
plan's own clause: *"treat the architecture decisions below as project
constraints unless the Phase 3 proposal identifies a concrete technical
conflict."*

### 13.1 ENet is the transport that was being described

Reliability layered by protocol over unreliable datagrams, with a reliable path
where it is needed, is what ENet *is* — and Godot ships it (`modules/enet`,
verified at tag `4.7.2-stable`).

**Per-message delivery.** `ENetPacketPeer.send(channel, packet, flags)`:

| Flag | Delivery |
|---|---|
| `FLAG_RELIABLE` | reliable, ordered — retransmitted until acknowledged |
| *(no flag)* | **unreliable but sequenced** — stale packets dropped, never redelivered |
| `FLAG_UNSEQUENCED` | unreliable, unsequenced |
| `FLAG_UNRELIABLE_FRAGMENT` | fragmenting permitted on an unreliable packet |

Chosen per message, on independent channels — the whole of §14.

### 13.2 One process, one port, many lobbies

`ENetConnection` wraps a raw `ENetHost` and exposes what a multi-lobby server
needs:

| Method | Use |
|---|---|
| `create_host_bound(bind_ip, port, max_peers, max_channels, …)` | **one** host on **one** UDP port |
| `service(timeout)` | pump connect / receive / disconnect on the server tick |
| `get_peers()` | every connected `ENetPacketPeer` |
| `channel_limit()` | the lanes in §14 |
| `refuse_new_connections()` | capacity enforcement at the transport edge |
| `bandwidth_limit()`, `compress()` | throttling, and ENet's built-in range coder |
| `dtls_server_setup()` | **DTLS encryption** — one of QUIC's real advantages, natively |

**The design.** One `ENetConnection` host owned by the `GameServer`. A peer binds
to exactly one `GameInstance` when its join token validates, and the router
resolves peer → instance on every received packet. Lobbies are isolated by
**ownership, not by socket** — which turns §22's rule ("a connection resolves to
exactly one `game_id`") into the only thing the code can express, rather than an
invariant somebody has to maintain.

**Rejected: `ENetMultiplayerPeer` with one `MultiplayerAPI` per lobby.** Godot
supports scoping a `MultiplayerAPI` to a scene subtree
(`SceneTree.set_multiplayer(api, root_path)`; nesting disallowed, siblings fine),
so it would work. Two reasons not to: `create_server(port, …)` **binds a port per
peer**, so 20 lobbies means 20 UDP ports to allocate, firewall and advertise; and
it pulls in the high-level RPC and `MultiplayerSynchronizer` replication, which
couple gameplay to the scene tree and undercut §11 — the model this rebuild
exists to get right.

### 13.3 Rejected alternatives

**Custom QUIC (msquic).** MIT, v2.6.1, actively maintained — and not needed here.
Unreliable datagrams, independent lanes and encryption are all native via ENet,
so adopting it means a substantial cross-platform C integration plus a GDExtension
transport shim to obtain capabilities the engine already ships.

**WebSocket (TCP).** What the current game uses. Head-of-line blocking makes one
lost packet delay every later one on the connection — the wrong shape for 30 Hz
snapshots. Worth recording, though, that the live game runs its entire netcode
over it and nobody has complained about the transport; the requirement has more
headroom than the theory suggests.

**WebRTC DataChannel.** Was the browser answer; out of scope with the native
decision. If a web client ever returns it drops in behind the same transport
interface — Godot ships `WebRTCMultiplayerPeer`, unreliable delivery is
available, and the Go API is the natural signalling server. The protocol above
the transport would not change.

**WebTransport.** Does not exist in Godot —
[godot-proposals#3899](https://github.com/godotengine/godot-proposals/issues/3899),
open since 2022-01-31, still open at 2026-08-05, unimplemented. Recorded so the
question is not reopened from memory later.

### 13.4 Downstream

`shared/networking/` is a thin transport interface with **one** implementation.
The interface stays because it costs nothing and is the seam both the WebRTC and
QUIC analyses above assumed — not speculative generality.

## 14. Reliable and unreliable lanes

| Traffic | Delivery | ENet |
|---|---|---|
| Input samples (60 Hz) | unreliable, sequenced | channel 0, no flag |
| Snapshots (30 Hz) | unreliable, sequenced | channel 0, no flag |
| Handshake, auth, capacity | reliable | channel 1, `FLAG_RELIABLE` |
| Match/round events, kills, chat | reliable | channel 2, `FLAG_RELIABLE` |
| Map / baseline transfer | reliable, bulk | channel 3, `FLAG_RELIABLE` |

Newer input supersedes older, so a lost input packet must never block a later
one; likewise a lost snapshot must not hold a newer one behind it.
Unreliable-sequenced gives exactly that — ENet drops a stale packet rather than
delivering it late.

Separate reliable channels exist so a bulk baseline transfer cannot delay a
round-start event queued behind it. That independence is what channels are for.

## 15. Protocol and serialization

**Direction given:** the Game API speaks JSON; the Game Server speaks a binary
protocol with a header carrying size and message type. The two need not align.
That is adopted, and it removes a dependency the earlier draft carried.

### 15.1 Game API — JSON over HTTPS

Plain JSON request/response. It is a control plane: a handful of calls per player
per session, human-readable in a log or a `curl`, trivially versioned by URL
(`/v1/…`), and readable by any tool without a schema compiler. There is no
argument for binary here — the traffic is negligible and debuggability outranks
bytes at this boundary.

### 15.2 Game Server — one binary framing, two lanes

Framing differs between the two QUIC primitives, because QUIC already solves
part of it:

**Reliable streams** are a byte pipe, so they need explicit framing:

```
u16  size        payload bytes that follow
u8   type        message type
u8   flags
...  payload
```

**Unreliable packets** are already length-delimited by the transport — true of
both ENet packets and QUIC datagrams — so a size field would be dead weight on
the highest-frequency traffic in the game. Omitted deliberately:

```
u8   type
u8   flags
u16  seq         per-connection, wrapping; stale/reorder rejection
u32  tick        simulation tick this refers to
...  payload
```

**Protocol version is negotiated once** in the handshake on the control stream,
not repeated per message. It cannot change mid-connection, and two bytes at
30 Hz across every client is real bandwidth spent on a constant.

### 15.3 Payload encoding — fixed layout, quantised

Little-endian, fixed field order per type, no self-description on the wire. The
snapshot entry is the one that matters:

| Field | Type | Bytes |
|---|---|---|
| participant id | `u8` | 1 |
| flags (alive, crouched, protected, special armed, special charging, bot) | `u8` | 1 |
| position x/y/z | `3 × u16` quantised over map bounds | 6 |
| yaw | `u16` (full circle) | 2 |
| pitch | `u16` (clamped ±90°) | 2 |
| health | `u8` | 1 |
| kills / deaths | `2 × u16` | 4 |
| | **total** | **17** |

`u8` id is sufficient — `HARD_MAX_PLAYERS` is 16 (`server.js:105`).
Map bounds come from the map data already shared by both sides
(`maps-loader.js`), so the quantisation range needs no extra
negotiation.

**The name is the hidden cost in the current build.** Today every snapshot
re-sends `n: 'BOT Vortex'` for every player, 30 times a second, for a string that
changes when someone joins. Names move to the join event and the baseline.

Measured against the real current payload (150 B/player, counted from the
`arr.push({…})` in `server.js`):

| Players | Today (JSON, 30 Hz) | Binary (17 B + 8 B header) |
|---|---|---|
| 8 | ~39 KB/s per client | ~4.3 KB/s |
| 12 | ~56 KB/s per client | ~6.3 KB/s |
| 16 | ~74 KB/s per client | ~8.2 KB/s |

Roughly a **9× reduction**, before any delta encoding.

### 15.4 Deliberately deferred

**Delta encoding against the last acknowledged baseline** would cut this further —
most players do not change most fields between two 33 ms snapshots. It is
deferred because it requires per-connection baseline tracking and an ack channel,
and it is a pure optimisation on top of a format that already fits comfortably.
Revisit if the 16-player figure becomes a problem; the framing above does not
have to change to add it (a flag bit and a baseline sequence in the header cover
it).

### 15.5 How the codecs stay honest

One schema file describes every message and field. A small generator emits the
C++ encoder/decoder for the game server and client, and a second target for test
clients so the socket-level tests in §20 can be written without a C++ harness.
Hand-writing two codecs that must agree byte-for-byte is exactly the kind of
duplication that drifts silently — the current build avoids the same trap by
sharing `hitbox.js` verbatim between client and server rather than porting it.

**Rejected:** FlatBuffers/Protobuf/Cap'n Proto for the game protocol. All three
are good at schema evolution across loosely-coupled services; none is needed for
a client and server that ship together, version-gate at the handshake, and send
fixed-shape messages. They would add a dependency and a build step for a problem
this protocol does not have. JSON on the hot path is rejected by the table above.

**Non-negotiable:** never serialise Godot `Node`s, `Variant`s or scene internals
onto the wire.

## 16. Tick, prediction, reconciliation

**Preserve the current rates — they are the measured feel:**

| Parameter | Today | Proposal |
|---|---|---|
| Simulation tick | 60 Hz fixed (`server.js:75`) | Unchanged |
| Input send rate | 60 Hz (`game.js`) | Unchanged |
| Snapshot rate | 30 Hz (`SNAP_EVERY=2`, `server.js:90`) | Unchanged, now delta-encoded |
| Interpolation delay | 80 ms (`game.js:3414`) | Unchanged |
| Max lag-comp rewind | 300 ms (`server.js:94`) | Unchanged |
| Position history | 1000 ms (`server.js:95`) | Unchanged |

The server already rewinds every target to where the shooter actually saw it —
`rewindPlayer()` blends the two straddling history samples, and the client sends
its own `lag = INTERP_DELAY_MS + netPing/2` with each shot (`game.js:3006`). That
model is correct and should be carried over intact.

**What changes:** today the client does *not* reconcile — it predicts locally and
the server never corrects position, because the server trusts client position
(`server.js` `state` handler assigns `pl.x/y/z` directly). That is the single
largest correctness gap in the current build and the reason the new server must
own movement: input → server integrates with `shared/game-core` → snapshot
carries authoritative position + last-processed input sequence → client replays
unacknowledged inputs from that state. Errors under a threshold are smoothed;
larger ones snap.

All of these live in one tuning resource, not scattered constants.

## 17. Delayed lobby persistence

A versioned `LobbySnapshot` produced *from owned state*, never by serialising
engine objects:

```
schema_version, snapshot_seq, taken_at,
game_id, display_name, mode, map_id,
max_players, max_spectators, rules{win_rounds|kill_target, bots, bots_shoot},
lifecycle_state (waiting|active|ending),
match{match_id, score_blue, score_red, round_num}
participants[]{participant_id, display_name, team, kills, deaths, is_bot}
```

Written on a **low-priority path**: a coalescing writer with a configurable
interval plus selected coarse lifecycle events, never on the tick path, never
blocking simulation. Exposes `last_persisted_at`, `last_persisted_version`, write
latency, failures and queue depth. A persistence failure is loud in metrics and
does not kill a healthy match.

Explicitly **not** persisted: per-tick transforms, QUIC connection objects,
`Node` references, input packets.

## 20. Testing

The current repo carries 254 assertions across three suites and they are worth
studying as a specification — particularly `test/live.test.mjs`, which drives the
real server over real sockets, and `test/browser.test.mjs`, which drives a real
browser with real input. The equivalents:

| Class | Scope |
|---|---|
| Unit (C++) | `game-core` movement, hitbox, rules — no engine, no display. |
| Protocol | Encode/decode, truncation, corruption, bad type, oversize, stale sequence, incompatible version. |
| Lifecycle | Create/destroy matches and rounds repeatedly; assert owned state is *gone*, not reset. |
| Cross-lobby isolation | Concurrent `GameInstance`s; prove ids and state cannot cross. |
| Capacity | Create 20, reject the 21st, destroy at random, reuse freed slots immediately. |
| Dedicated soak | Thousands of matches in one preloaded 1/1 instance; assert flat memory and no accumulation. |
| Network conditions | Latency, jitter, loss, reordering, duplication against reconciliation. |
| Persistence | Delayed writes, coalescing, stale versions, failures without stalling. |
| Integration | API → create → discover → join → QUIC → play → end → cleanup. |

Two lessons from today's work on the existing suite, worth carrying: a test that
waits *n* seconds for an emergent event needs a window justified by measurement
(an 8 s bot-shooting window flaked two different ways under load; 20 s is stable
and also makes the matching negative assertion meaningful), and a harness that
leaks a resource silently starves its own later sections.

## 22. Security boundaries

- Never trust client position, health, damage, kills, score, weapon ownership or
  spawn validity. **This is a change from today**, where the server accepts
  client position (§16).
- Authenticate joins (short-lived tokens) and Game Server registration.
- Validate type, length, protocol version and state legality before applying any
  message.
- Rate-limit per connection; one malformed client must not destabilise a
  multi-lobby process.
- A connection resolves to exactly one `game_id`; a packet can never mutate
  another `GameInstance`. With the §13.3 routing this is structural: the router
  maps peer → instance, and a packet has no field that could name a different one.
- Transport encryption via `ENetConnection.dtls_server_setup()` (DTLS), so
  dropping QUIC does not mean dropping encryption.
- Management and debug surfaces off the public path.
- Keep the existing chat discipline: 50-char cap, control/bidi codepoints
  stripped server-side, token-bucket rate limit, and **rendered as text, never
  markup** (`public/game.js`, chat section).

## 23. Risks and decisions needing approval

1. **godot-cpp has no stable tag for Godot 4.7 (§7).** Recommendation is 4.7.2
   engine + `godot-4.5-stable` bindings at `api_version=4.5`, which upstream
   documents as supported. The conservative alternative is pinning the engine to
   4.5-stable for an exactly matched pair. **The one version decision left.**

2. **Map authoring moves into the Godot editor (§2.3),** which retires the bespoke
   web map editor (`editor-server.js`, `public/editor.js`, and the map-authoring
   skill). Net simplification, but it is working software being deliberately
   dropped, so it should be an explicit call rather than a silent consequence.

3. **Server-authoritative movement is a behaviour change.** Today the server
   accepts client position; making it authoritative is correct but will alter
   feel under latency until reconciliation is tuned. Milestone 8 exists for this
   and should not be compressed.
4. **The rebuild target is moving.** The PlayCanvas game is live and shipped
   twelve features today. This document was written against `laser-arena`
   `a44e11b`. Recommend tagging that commit in the reference repository (e.g.
   `reference/plan-2026-08-30`) so the baseline is named rather than implied, and
   re-reading deliberately when it moves.
5. **Animation bake (§2.1)** assumes `AnimationTree` bone filtering reproduces
   the current gun-ready look. Needs a spike before Milestone 9 is estimated.
6. **Emoji glyphs in the HUD (§2.4)** need vector replacements or a font that
   covers them.
7. **Two codecs from one schema (§15.5)** need a generator; writing it is a
   small task but it is a task, and it belongs in Milestone 0 rather than being
   discovered in Milestone 5.
8. **20 lobbies in one process** is untested for this workload; the capacity
   number should be treated as a target to be validated by the soak test, not a
   guarantee.
9. **Does "native" include mobile?** Godot exports to Android and iOS as
   natively as it does to desktop, and the current game has a complete, recently
   tuned touch scheme — landscape gate, movement stick, drag-to-aim with
   tap-to-shoot, and a button layout proven not to overlap at 844×390 and
   667×375 (§3.5). If mobile is in scope that work ports; if desktop-only, §3.5
   and the touch half of Milestone 10 come out of the plan entirely. A real
   scope difference, worth naming rather than assuming.
